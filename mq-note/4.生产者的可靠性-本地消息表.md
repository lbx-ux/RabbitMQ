## 1. 为什么有了 Confirm/Return 还不够

先复习笔记 4 的结论：Confirm/Return 只能「**感知**」丢失，不能「**挽回**」丢失。

把三种真实事故摆在它面前，就看出无能为力了：

| # | 事故场景 | Confirm/Return 能做什么 | 为什么不够 |
|---|---|---|---|
| 1 | ack 回执在网络中丢了（MQ 其实收到了） | 收不到回执，你只知道「没回音」 | 无法区分「MQ 没收到」和「ack 丢了」，不知道该不该重发 |
| 2 | 消息还没发出去，进程就崩了 | 什么都不触发（人都死了，谁来收回执？） | 业务已提交（钱扣了），消息却永远发不出去 |
| 3 | 就算感知到失败，回调里该干什么？ | —— | **回调里拿不到原始消息**，想重发都不知道重发什么 |

第 3 点是最容易被忽略的：Confirm 回调只给你一个 `messageId` 和 ack/nack 标志。
要重发，你得能**重新拿到那条消息的完整内容、目标交换机、路由键**——这要求消息在发送前就被持久化在某处。

再往深一层，这本质上是**分布式事务**问题：

```
扣款（写数据库） + 发 MQ 消息（网络操作） = 两个无法用同一个事务保证的动作

BEGIN TRANSACTION
    UPDATE account SET balance = balance - 100;   -- ① 数据库操作，可回滚
    rabbitTemplate.convertAndSend(...);           -- ② 网络操作，不受事务管辖！
COMMIT                                            -- 若 commit 失败，②已经发出去收不回来
```

事务能回滚 ①，但管不住 ②。反过来，① 成功后进程崩溃，② 根本没执行——
「钱扣了，通知却没发」，这就是要解决的核心矛盾。

## 2. 核心思想一句话

> **利用本地数据库事务，保证「业务数据」与「消息记录」原子性地一起落盘；**
> **再通过 Confirm 闭环 + 定时补偿，保证消息最终一定投递成功。**

翻译成大白话：**寄快递前先把单号和包裹拍照存档，没收到签收回执就照着照片重寄，直到签收或转人工。**

它把「发消息」这个**不确定的网络操作**，拆成了：

1. 「写数据库」这个**确定的本地操作**（事务保证，崩溃也不怕）；
2. 一个**可重复执行的投递任务**（失败了就再来，直到确认）。

消息记录落了库，就有了「重发的依据」「重试次数的账本」「人工兜底的现场」。

## 3. 表设计（逐字段讲解）

```sql
CREATE TABLE IF NOT EXISTS `lab4_local_message` (
  id              BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  message_id      VARCHAR(64)  NOT NULL COMMENT '消息唯一标识(=CorrelationData.id)',
  message_type    VARCHAR(32)  NOT NULL COMMENT '消息类型，如 ORDER_PAID',
  content         TEXT         NOT NULL COMMENT '消息体JSON(与发到MQ的内容一字不差)',
  exchange        VARCHAR(64)  NOT NULL COMMENT '目标交换机',
  routing_key     VARCHAR(64)  NOT NULL COMMENT '目标路由键',
  status          TINYINT      NOT NULL DEFAULT 0 COMMENT '0发送中 1已确认 2失败 3死信',
  retry_count     INT          NOT NULL DEFAULT 0 COMMENT '已补偿重试次数',
  create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  next_retry_time DATETIME     NULL COMMENT '下次允许重试的时间(指数退避)',
  PRIMARY KEY (id),
  UNIQUE KEY uk_message_id (message_id),
  KEY idx_status_next_retry (status, next_retry_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT 'lab4本地消息表';
```

逐个字段说清楚「为什么」：

| 字段 | 为什么必须存在 |
|---|---|
| `message_id` | **全流程的线索**。发送时作为 `CorrelationData.id` 传给 MQ，Confirm 回执带回来，靠它反查这条记录改状态。没有它，回执和数据库就断链了 |
| `content` | **重发的依据**。Confirm/Return 回调里拿不到原消息，只有库里存了完整 JSON，补偿任务才能原样重发 |
| `exchange` + `routing_key` | 同上——重发还需要知道「发到哪」 |
| `message_type` | 一张表承载所有业务消息（支付成功/退款/发货…），按类型区分，便于统计和对不同类型定制重试策略 |
| `status` | 状态机的载体，见 §6 全景图 |
| `retry_count` | 重试的账本。无限重试会打爆 MQ，必须记账、设上限 |
| `next_retry_time` | **指数退避**的落点。MQ 宕机时不能每 30 秒傻傻地撞，间隔要越拉越长 |

**两个索引是两把刀**：

- `uk_message_id` 唯一索引：防同一条消息重复落库（业务重试导致 saveMessage 被调两次时直接报错拦截）；
- `idx_status_next_retry` 联合索引：补偿任务每 30 秒执行一次
  `WHERE status IN (0,2) AND next_retry_time < now()`，没有它，表大了以后全表扫描拖垮数据库。

## 4. 正常流程全链路（时序图）

```
业务方法(如支付)          本地消息表              MQ Broker          Confirm回调
    │                        │                      │                    │
    │ ①开启事务 @Transactional│                      │                    │
    │──saveMessage()───────>│                      │                    │
    │   INSERT status=0      │                      │                    │
    │   (业务数据同事务落库)   │                      │                    │
    │ ②COMMIT ──────────────>│ 记录已持久化✅        │                    │
    │                        │                      │                    │
    │ ③afterCommit 钩子触发   │                      │                    │
    │──send(消息+CorrelationData)───────────────────>│ 消息入队           │
    │                        │                      │                    │
    │                        │                      │──basic.ack────────>│
    │                        │                      │                    │ ④Future完成
    │                        │<─────UPDATE status=1 CONFIRMED─────────────│
    │                        │                      │                    │
    ▼ 正常路径：一次发送，一次确认，闭环完成（约几十毫秒）
```

记住这条主线，后面所有异常场景都是在主线某个环节「剪一刀」，看补偿怎么接住。

## 5. 代码实现（四大组件）

对照 `mq-labs/lab4-producer`，实现只需要四个角色：

```
LocalMessageSender（发送器）      ← 核心，组合了落库/发送/回调/补偿
CompensationTask（定时任务）      ← 每30秒扫描兜底
ProducerController（实验入口）    ← 触发各种场景
MqCallbackConfig（全局Return）    ← 路由失败告警
```

### 5.1 落库：saveMessage（事务内调用）

```java
public void saveMessage(String messageId, String messageType,
                        Object payload, String exchange, String routingKey) {
    LocalMessage msg = new LocalMessage();
    msg.setMessageId(messageId);
    msg.setMessageType(messageType);
    // 消息体统一转 JSON 存储 —— 与真正发到 MQ 的内容保持一字不差
    msg.setContent(objectMapper.writeValueAsString(payload));
    msg.setExchange(exchange);
    msg.setRoutingKey(routingKey);
    msg.setStatus(0); // SENDING
    msg.setRetryCount(0);
    msg.setCreateTime(LocalDateTime.now());
    msg.setNextRetryTime(LocalDateTime.now().plusSeconds(30)); // 30s 未确认才允许补偿
    localMessageMapper.insert(msg);
}
```

三个细节：

1. **`next_retry_time = now + 30s`**：给正常路径留缓冲。Confirm ack 通常几十毫秒就回来，
   如果补偿任务扫得太激进，会把「还在路上的消息」误判为失败，造成无谓重发。
2. **content 存的是「将要发出去的那个对象」序列化后的 JSON**，不是消息的描述或摘要——
   补偿时要原样重发，存什么就得发什么。
3. 这个方法**必须**在业务事务内被调用（见 §5.2），单独调用毫无可靠性意义。

### 5.2 事务 + 发送时序：sendAfterCommit（最容易写错的一步）

先看**错误写法**——很多人第一直觉是在事务内直接发：

```java
@Transactional
public void pay(...) {
    deductBalance();                    // 业务操作
    sender.saveMessage(...);            // 落库
    sender.send(...);                   // ❌ 事务还没提交就发送了！
}
```

错在哪？**发送成功 → 之后 COMMIT 失败/回滚**：数据库里业务没发生，
但消费者已经收到了消息——「**幽灵消息**」，业务上等于凭空捏造了一笔支付。

正确写法——注册「事务提交后」钩子：

```java
public void sendAfterCommit(String messageId, String messageType,
                            Object payload, String exchange, String routingKey) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                send(messageId, exchange, routingKey, payload);  // 提交成功才发送
            }
        });
    } else {
        send(messageId, exchange, routingKey, payload);  // 无事务环境直接发
    }
}
```

两个半环拼在一起才是完整的：

- 落库在事务内 → **业务成功 ⟺ 消息记录一定在**（原子性，解决进程崩溃场景）；
- 发送在提交后 → **不会发出业务上不存在的消息**（解决幽灵消息）。

业务方使用只要三行：

```java
@PostMapping("/order")
@Transactional(rollbackFor = Exception.class)
public String order(...) {
    sender.saveMessage(messageId, "ORDER_PAID", payload, ORDER_EXCHANGE, ORDER_KEY); // 第1步：事务内落库
    sender.sendAfterCommit(messageId, "ORDER_PAID", payload, ORDER_EXCHANGE, ORDER_KEY); // 第2步：注册钩子
    return "下单完成";   // 事务在此提交 → afterCommit 自动触发发送
}
```

### 5.3 发送 + Confirm 闭环：send（局部 Future 回调）

```java
public void send(String messageId, String exchange, String routingKey, Object payload) {
    // 1. CorrelationData 的 id = messageId —— Confirm 闭环的关键线索
    CorrelationData cd = new CorrelationData(messageId);

    // 2. 局部 Confirm 回调（Boot 2.7 用 getFuture().addCallback）
    cd.getFuture().addCallback(result -> {
        if (result != null && result.isAck()) {
            updateStatus(messageId, 1);   // CONFIRMED，终点
        } else {
            updateStatus(messageId, 2);   // FAIL，等补偿任务重发
        }
    }, ex -> {
        updateStatus(messageId, 2);       // Future 异常（连接断开等）也标记失败
    });

    // 3. 发送时必须携带 cd，否则回调永远不触发
    rabbitTemplate.convertAndSend(exchange, routingKey, payload, cd);
}
```

呼应《4.生产者的可靠性》§3 的三个高频踩坑：

1. **不带 cd 发送 = 回调永远不触发**——三参重载 `convertAndSend(exchange, key, msg)` 没有回执通道；
2. **回调触发 ≠ 发送成功**——要看 `result.isAck()`，nack 也走这个回调；
3. **cd.getId() 必须等于本地消息表的 message_id**——回执到达时全靠它反查记录。

### 5.4 补偿：retrySend + 定时扫描

```java
/** 每 30 秒扫一次（生产建议 1~5 分钟，视消息量而定） */
@Scheduled(fixedDelay = 30_000)
public void compensate() {
    sender.findTimeoutUnconfirmed().forEach(sender::retrySend);
}

/** 扫描条件：状态还没闭环 + 到了允许重试的时间 */
public List<LocalMessage> findTimeoutUnconfirmed() {
    return localMessageMapper.selectList(
        Wrappers.<LocalMessage>lambdaQuery()
            .in(LocalMessage::getStatus, 0, 2)              // SENDING 或 FAIL
            .lt(LocalMessage::getNextRetryTime, LocalDateTime.now()));
}

/** 补偿重发一条：指数退避，最多 3 次，耗尽转 DEAD 人工 */
public boolean retrySend(LocalMessage msg) {
    if (msg.getRetryCount() >= 3) {
        msg.setStatus(3);                                    // DEAD，转人工
        localMessageMapper.updateById(msg);
        return false;
    }
    Object payload = objectMapper.readValue(msg.getContent(), Object.class); // 原样还原
    send(msg.getMessageId(), msg.getExchange(), msg.getRoutingKey(), payload); // 重发
    msg.setRetryCount(msg.getRetryCount() + 1);
    long backoff = 30_000L * (1L << msg.getRetryCount());    // 30s → 60s → 120s
    msg.setNextRetryTime(LocalDateTime.now().plusNanos(backoff * 1_000_000));
    localMessageMapper.updateById(msg);
    return true;
}
```

要点拆解：

- **扫描条件为什么是 `status IN (0,2)`？** 0（SENDING）覆盖「ack 丢了/进程崩了/还没来得及发」，
  2（FAIL）覆盖「收到 nack/发送抛异常」。1（CONFIRMED）已闭环不碰，3（DEAD）等人工不碰。
- **为什么按 `next_retry_time` 过期才扫？** 指数退避的实现就落在这里：每次重发把
  `next_retry_time` 推远一倍，MQ 长时间宕机时重试频率自动衰减（30s→60s→120s），不雪上加霜。
- **为什么从库里还原 payload 而不是重发内存对象？** 补偿任务通常在另一个线程/另一次进程生命周期里跑，
  内存对象早没了；库里那份 JSON 才是唯一可信的「原文」。
- **重试上限 3 次 + DEAD 状态**：3 次都失败大概率是配置错误/严重故障，机器重试无意义，
  转人工排查（就像笔记 5 消费端的 error.queue 思路——机器兜到底，人兜最后一步）。

## 6. 异常场景逐个击破（对照实验）

表设计 + 四大组件就位后，把 §1 的三种事故重新放回来，看系统怎么接住：

### 场景一：消息还没发出去，进程崩了

```
时间线：saveMessage 落库(status=0) → COMMIT → ✖ 进程崩溃（send 从未执行）
恢复：进程重启 → 30 秒后补偿任务扫描 → status=0 且 next_retry_time 已过期 → 重发 → ack → status=1
```

消息记录跟着业务事务一起落了盘，崩溃杀不掉它——**这就是「先落库」的意义**。

### 场景二：ack 在网络中丢了

```
时间线：send 发出 → MQ 收到入队 → ack 丢失 → 生产者这边 status 停在 0
恢复：补偿任务 30 秒后扫描 → 误判为「没送到」→ 重发 → MQ 会收到两遍
```

注意：**系统「不知道」这是误判，也不可能知道**——ack 丢了和没送到，在生产者视角完全一样。
所以必然产生重复投递，这正是「消费端必须幂等」的根本原因（见 §8）。

### 场景三：MQ 收到但返回 nack（交换机内部异常）

```
时间线：send → nack 回执 → Future 回调立即触发 → status=2（不用等扫描）
恢复：补偿任务扫到 status=2 → 重发
```

局部 Confirm 回调的价值：把「感知失败」从「最慢 30 秒（定时扫描）」提前到「毫秒级」，
但**无论多快感知，挽回动作都只有一种——从库里拿原文重发**。

### 场景四：路由键写错（Return 场景）

```
时间线：send → 交换机收到但路由不到队列 → Return 退回（同时 ack=true）
```

这个场景 Confirm 会给 **ack**（消息确实到达交换机了），status 会变成 1——
**本地消息表管不到路由失败**！它由 Return 回调负责：全局 ReturnsCallback 打日志告警，
生产上还应在回调里把对应 messageId 标记为 FAIL，交给补偿链路。

> 三个回调各管一段：**Return 管路由、Confirm 管送达、本地消息表管最终一致**，谁也替代不了谁。

```bash
# Return 场景：路由失败但 ack（对照场景四）

```

## 7. 状态机全景与人工兜底

```
                    ┌─────────────────────────────────────────┐
                    │  0 SENDING（落库后的初始状态）              │
                    └────┬────────────────────┬───────────────┘
                  ack ✓  │                    │ nack / 发送异常 / 30s 超时
                         ▼                    ▼
              ┌────────────────┐    ┌──────────────────────────┐
              │ 1 CONFIRMED ✅ │    │ 2 FAIL（等补偿扫描）        │
              │   (终点)       │    └────┬─────────────────────┘
              └────────────────┘         │ 补偿重发（retryCount+1，退避30s→60s→120s）
                                         │ 成功 → 1 / 依旧失败 → 保持2
                                         ▼ retryCount ≥ 3
                              ┌────────────────────┐
                              │ 3 DEAD（转人工）      │
                              │  修复后可手动重置状态  │
                              └────────────────────┘
```

DEAD 不是垃圾箱，是**人工处理队列**：故障修复后，把记录的 status 改回 2（或直接调重发接口），
消息还能被再次投出。本地消息表让「人」成为可靠性的最后一环，而不是让消息凭空消失。

## 8. 必须想通：补偿必然导致重复投递

回到场景二：你**永远无法**区分「MQ 没收到」和「MQ 收到了但 ack 丢了」。
补偿任务只能盲目重发——这是「宁可重复、不可丢失」的主动选择。

由此得出全篇最重要的公式：

> **发送端「至少一次」（At Least Once） + 消费端「幂等」 = 业务上「恰好一次」（Effectively Once）**

这两层是**配套工程**，缺一不可：

| 组合 | 结果 |
|---|---|
| 只有本地消息表（至少一次） | 消息重复，积分加两次、短信发两条 |
| 只有消费端幂等（不做可靠发送） | 消息丢了就是丢了，幂等无从谈起 |
| 两者结合 | 丢不了 + 不会重复 = 业务正确 ✅ |

所以看到本地消息表的代码时，请同时检查消费端有没有幂等设计（笔记 5 §4 的
Redis SETNX + 唯一索引）。这也是本项目 lab4 和 lab5 要连起来读的原因。

## 9. 生产环境补充事项（进阶）

教学版抓主干，真实生产还要补这几刀：

1. **表会无限膨胀**：CONFIRMED 记录要定期归档/删除（定时任务按 create_time 清理，保留 N 天）。
2. **扫描任务要分布式安全**：多实例部署时，多个补偿任务会同时扫到同一条记录并发重发。
   方案：`SELECT ... FOR UPDATE` 行锁、或用 `UPDATE status=0 WHERE id=? AND status=0` 的
   抢占式更新（更新到才重发）、或直接用 ShedLock/quartz 分布式调度。
3. **发送与补偿都建议加日志埋点 + 监控告警**：DEAD 数量、SENDING 积压时长是最敏感的故障指标。
4. **content 里的敏感字段要加密**：本地消息表里躺着全量业务报文，按安全合规处理。
5. **事务消息的替代方案**：RocketMQ 自带事务消息（半消息 + 回查），本质思路与本地消息表相同
   （先落半消息、再提交、回查兜底），用中间件替你管了这张「表」。理解了本地消息表，
   RocketMQ 事务消息就是换了个壳。

## 10. 全文总结（一张图）

```
┌─────────────────────── 本地消息表 = 可靠性的「账本」 ───────────────────────┐
│                                                                          │
│  业务事务内： saveMessage()      ← 业务成功 ⟺ 记录一定在（原子性）           │
│  事务提交后： send() + cd        ← 不发幽灵消息；cd.id=messageId 闭环线索     │
│  Confirm 回执： updateStatus()   ← ack→1 闭环 / nack→2 等补偿              │
│  每30秒：     扫描 0/2 + 过期    ← 指数退避重发，≤3次，耗尽转 DEAD 人工       │
│                                                                          │
│  发送端至少一次 + 消费端幂等 = 业务恰好一次                                  │
└──────────────────────────────────────────────────────────────────────────┘

一句话记忆：**先把「要发的话」写进账本，再说出去；说出去要回执；没回执就照账本再说一遍；
说三遍还没成，拿给老板（人工）看。**
```
