# 本地消息表

**为什么有了 Confirm/Return 还不够**

Confirm/Return 只能「**感知**」丢失，不能「**挽回**」丢失。

把三种真实事故摆在它面前，就看出无能为力了：

| # | 事故场景 | Confirm/Return 能做什么 | 为什么不够 |
|---|---|---|---|
| 1 | ack 回执在网络中丢了（MQ 其实收到了） | 收不到回执，你只知道「没回音」 | 无法区分「MQ 没收到」和「ack 丢了」，不知道该不该重发 |
| 2 | 消息还没发出去，进程就崩了 | 什么都不触发（人都死了，谁来收回执？） | 业务已提交（钱扣了），消息却永远发不出去 |
| 3 | 就算感知到失败，回调里该干什么？ | —— | **回调里拿不到原始消息**，想重发都不知道重发什么 |

第 3 点是最容易被忽略的：Confirm 回调只给你一个 `messageId` 和 ack/nack 标志。
要重发，你得能**重新拿到那条消息的完整内容、目标交换机、路由键**——这要求消息在发送前就被持久化在某处。

再往深一层，这本质上是**分布式事务**问题：

```
扣款（写数据库） + 发 MQ 消息（网络操作） = 两个无法用同一个事务保证的动作

BEGIN TRANSACTION
    UPDATE account SET balance = balance - 100;   -- ① 数据库操作，可回滚
    rabbitTemplate.convertAndSend(...);           -- ② 网络操作，不受事务管辖！
COMMIT                                            -- 若 commit 失败，②已经发出去收不回来
```

事务能回滚 ①，但管不住 ②。反过来，① 成功后进程崩溃，② 根本没执行——「钱扣了，通知却没发」，这就是要解决的核心矛盾。



## 1. 核心思想

> **利用本地数据库事务，保证「业务数据」与「消息记录」原子性地一起落盘；**
> **再通过 Confirm 闭环 + 定时补偿，保证消息最终一定投递成功。**

翻译成大白话：**寄快递前先把单号和包裹拍照存档，没收到签收回执就照着照片重寄，直到签收或转人工。**

它把「发消息」这个**不确定的网络操作**，拆成了：

1. 「写数据库」这个**确定的本地操作**（事务保证，崩溃也不怕）；
2. 一个**可重复执行的投递任务**（失败了就再来，直到确认）。

消息记录落了库，就有了「重发的依据」「重试次数的账本」「人工兜底的现场」。



## 2. 表设计

```sql
CREATE TABLE IF NOT EXISTS `local_message` (
  id              BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  message_id      VARCHAR(64)  NOT NULL COMMENT '消息唯一标识(=CorrelationData.id)',
  message_type    VARCHAR(32)  NOT NULL COMMENT '消息类型，如 ORDER_PAID',
  content         TEXT         NOT NULL COMMENT '消息体JSON(与发到MQ的内容一字不差)',
  exchange        VARCHAR(64)  NOT NULL COMMENT '目标交换机',
  routing_key     VARCHAR(64)  NOT NULL COMMENT '目标路由键',
  status          TINYINT      NOT NULL DEFAULT 0 COMMENT '0发送中 1已确认 2失败 3死信',
  retry_count     INT          NOT NULL DEFAULT 0 COMMENT '已补偿重试次数',
  create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  next_retry_time DATETIME     NULL COMMENT '下次允许重试的时间(指数退避)',
  PRIMARY KEY (id),
  UNIQUE KEY uk_message_id (message_id),
  KEY idx_status_next_retry (status, next_retry_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT '本地消息表';
```

逐个字段说清楚「为什么」：

| 字段 | 为什么必须存在 |
|---|---|
| `message_id` | **全流程的线索**。发送时作为 `CorrelationData.id` 传给 MQ，Confirm 回执带回来，靠它反查这条记录改状态。没有它，回执和数据库就断链了 |
| `content` | **重发的依据**。Confirm/Return 回调里拿不到原消息，只有库里存了完整 JSON，补偿任务才能原样重发 |
| `exchange` + `routing_key` | 同上——重发还需要知道「发到哪」 |
| `message_type` | 消息类型分类，用于方便按业务过滤、日志排查或路由到不同的处理逻辑。 |
| `status` | 消息生命周期状态 |
| `retry_count` | 重试的次数。无限重试会打爆 MQ，必须记账、设上限 |
| `next_retry_time` | **指数退避**的落点。MQ 宕机时不能每 30 秒傻傻地撞，间隔要越拉越长 |

**两个索引是两把刀**：

- `uk_message_id` 唯一索引：防同一条消息重复落库（业务重试导致 saveMessage 被调两次时直接报错拦截）；
- `idx_status_next_retry` 联合索引：补偿任务每 30 秒执行一次`WHERE status IN (0,2) AND next_retry_time < now()`，没有它，表大了以后全表扫描拖垮数据库。



## 3. 正常流程全链路

```
业务方法(如支付)          本地消息表              MQ Broker          Confirm回调
    │                        │                      │                    │
    │ ①开启事务 @Transactional│                      │                    │
    │──saveMessage()───────>│                      │                    │
    │   INSERT status=0      │                      │                    │
    │   (业务数据同事务落库)   │                      │                    │
    │ ②COMMIT ──────────────>│ 记录已持久化✅        │                    │
    │                        │                      │                    │
    │ ③afterCommit 钩子触发   │                      │                    │
    │──send(消息+CorrelationData)───────────────────>│ 消息入队           │
    │                        │                      │                    │
    │                        │                      │──basic.ack────────>│
    │                        │                      │                    │ ④Future完成
    │                        │<─────UPDATE status=1 CONFIRMED─────────────│
    │                        │                      │                    │
    ▼ 正常路径：一次发送，一次确认，闭环完成（约几十毫秒）
```

记住这条主线，后面所有异常场景都是在主线某个环节「剪一刀」，看补偿怎么接住。

**核心流程分步拆解**

**1. 本地数据库事务提交（第 3~7 行）**

- **操作**：业务方法（如支付）开启事务，在保存业务数据的同时，向**本地消息表**插入一条记录，状态初始化为 `0`（未发送/发送中）。
- **关键**：业务数据和消息记录在**同一个数据库事务**里，要么一起成功，要么一起回滚。

**2. 事务提交后才发 MQ（第 9~10 行）**

- **操作**：利用 `@TransactionalEventListener` 或 `TransactionSynchronization.afterCommit()` 钩子，**等待本地事务完全提交（COMMIT）后**，再调用 MQ 发送消息。
- **目的**：保证“发出去的消息，数据库里一定有记录”。如果在事务内直接发 MQ，万一后续数据库回滚了，MQ 消息就已经取消不掉了。

**3. MQ 接收并应答（第 10~12 行）**

- **操作**：MQ Broker 收到消息并成功入队，异步给生产者返回一个 `basic.ack`（即 Confirm 确认）。

**4. 更新本地消息状态，形成闭环（第 13~14 行）**

- **操作**：生产者的 Confirm 回调函数被触发（或者异步 Future 完成），根据携带的 `CorrelationData`（消息 ID），去更新本地消息表的状态为 `1`（已确认/发送成功）。





## 4. 代码实现（四大组件）

**实现只需要四个角色：**

```
LocalMessageSender（发送器）      ← 核心，组合了落库/发送/回调/补偿
CompensationTask（定时任务）      ← 每30秒扫描兜底
ProducerController（实验入口）    ← 触发各种场景
MqCallbackConfig（全局Return）    ← 路由失败告警
```

```
[ 业务服务 ]
   │
   ├─ 1. 开启本地事务 @Transactional
   │     ├─ 修改业务数据 (如: 扣减余额)
   │     └─ 插入消息记录到 local_message (status = 0) saveMessage()
   ├─ 2. 提交本地事务 (此时业务数据和消息记录同时落库)
   │
   ├─ 3. afterCommit 钩子触发 -> 异步发送消息到 MQ
   │
   ├─ 4. MQ 收到消息，异步返回 Confirm ACK
   │     └─ 生产者收到 ACK -> 将 local_message 的 status 更新为 1
   │
   └─ 5. 【后台定时任务兜底】
         └─ 扫描 status=0 且已超时的记录 -> 重新发送 -> 达到最大重试次数标记为 3 (死信)
```



### 1. 落库：saveMessage

**实体类**

```java
@Data
@TableName("local_message")
public class LocalMessage {

    @TableId(type = IdType.AUTO)
    private Long id;

    /** 消息唯一标识（CorrelationData 的 id 与它相同，Confirm 回执靠它反查本表） */
    private String messageId;

    /** 消息类型 */
    private String messageType;

    /** 消息体（JSON 字符串，与真正发到 MQ 的内容一字不差） */
    private String content;

    /** 目标交换机 */
    private String exchange;

    /** 路由键 */
    private String routingKey;

    /** 状态：0=发送中(SENDING) 1=已确认(CONFIRMED) 2=失败(FAIL) 3=死信(DEAD) */
    private Integer status;

    /** 已重试次数 */
    private Integer retryCount;

    /** 创建时间 */
    private LocalDateTime createTime;

    /** 下次允许重试的时间（避免密集重试） */
    private LocalDateTime nextRetryTime;
}

```



```java
public void saveMessage(String messageId, String messageType,
                            Object payload, String exchange, String routingKey) {
    //payload就是消息的本体，这个看项目的具体要求
        try {
            LocalMessage msg = new LocalMessage();
            msg.setMessageId(messageId);
            msg.setMessageType(messageType);
            // 消息体统一转 JSON 存储（Hutool）—— 与真正发到 MQ 的内容保持一致
            msg.setContent(JSONUtil.toJsonStr(payload));
            msg.setExchange(exchange);
            msg.setRoutingKey(routingKey);
            msg.setStatus(0); // SENDING
            msg.setRetryCount(0);
            msg.setCreateTime(LocalDateTime.now());
            msg.setNextRetryTime(LocalDateTime.now().plusSeconds(30)); // 30s 未确认才允许补偿
            localMessageMapper.insert(msg);
            log.info("[本地消息表] 落库成功 messageId={} exchange={} routingKey={}",
                    messageId, exchange, routingKey);
        } catch (Exception e) {
            throw new RuntimeException("本地消息表落库失败", e);
        }
    }
```

三个细节：

1. **`next_retry_time = now + 30s`**：给正常路径留缓冲。Confirm ack 通常几十毫秒就回来，如果补偿任务扫得太激进，会把「还在路上的消息」误判为失败，造成无谓重发。
2. **content 存的是「将要发出去的那个对象」序列化后的 JSON**，不是消息的描述或摘要——补偿时要原样重发，存什么就得发什么。
3. 这个方法**必须**在业务事务内被调用，单独调用毫无可靠性意义。



### 2. 事务 + 发送时序：sendAfterCommit

先看**错误写法**——很多人第一直觉是在事务内直接发：

```java
@Transactional
public void pay(...) {
    deductBalance();                    // 业务操作
    sender.saveMessage(...);            // 落库
    sender.send(...);                   // ❌ 事务还没提交就发送了！
}
```

错在哪？**发送成功 → 之后 COMMIT 失败/回滚**：数据库里业务没发生，但消费者已经收到了消息——「**幽灵消息**」，业务上等于凭空捏造了一笔支付。

正确写法——注册「事务提交后」钩子：

```java
public void sendAfterCommit(String messageId, Object payload, String exchange, String routingKey) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                send(messageId, exchange, routingKey, payload);  // 提交成功才发送
            }
        });
    } else {
        send(messageId, exchange, routingKey, payload);  // 无事务环境直接发
    }
}
```

两个半环拼在一起才是完整的：

- 落库在事务内 → **业务成功 ⟺ 消息记录一定在**（原子性，解决进程崩溃场景）；
- 发送在提交后 → **不会发出业务上不存在的消息**（解决幽灵消息）。

业务方使用只要三行：

```java
private final LocalMessageSender sender;

    @PostMapping("/order")
    @Transactional(rollbackFor = Exception.class)
    public String order(@RequestParam(defaultValue = "ORD-1001") String orderNo) {
        String messageId = "PAY-" + UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        Map<String, Object> payload = new HashMap<>();
        payload.put("messageId", messageId);
        payload.put("orderNo", orderNo);
        payload.put("payAmount", 899900);

        // 第 1 步：事务内落库（本方法有 @Transactional，落库与「业务」同生共死）
        sender.saveMessage(messageId, "ORDER_PAID", payload,
                ProducerTopology.ORDER_EXCHANGE, ProducerTopology.ORDER_KEY);
        // 第 2 步：注册事务提交后自动发送（messageType 落库时已存，发送参数里不再重复）
        sender.sendAfterCommit(messageId, payload,
                ProducerTopology.ORDER_EXCHANGE, ProducerTopology.ORDER_KEY);
        return "下单完成 messageId=" + messageId;
    }
```



### 3. 发送 + Confirm 闭环：send

```java
public void send(String messageId, String exchange, String routingKey, Object payload) {
    // 1. CorrelationData 的 id = messageId —— Confirm 闭环的关键线索
    CorrelationData cd = new CorrelationData(messageId);

    // 2. 局部 Confirm 回调（Boot 2.7 用 getFuture().addCallback）
    cd.getFuture().addCallback(result -> {
        if (result != null && result.isAck()) {
            updateStatus(messageId, 1);   // CONFIRMED，终点
        } else {
            updateStatus(messageId, 2);   // FAIL，等补偿任务重发
        }
    }, ex -> {
        updateStatus(messageId, 2);       // Future 异常（连接断开等）也标记失败
    });

    // 3. 发送时必须携带 cd，否则回调永远不触发
    rabbitTemplate.convertAndSend(exchange, routingKey, payload, cd);
}
```

```java
/** 更新本地消息表状态（Confirm 回执按 messageId 反查记录后更新） */
public void updateStatus(String messageId, int status) {
    LocalMessage record = localMessageMapper.selectOne(
            Wrappers.<LocalMessage>lambdaQuery().eq(LocalMessage::getMessageId, messageId));
    if (record == null) {
        log.warn("[本地消息表] 找不到 messageId={} 的记录", messageId);
        return;
    }
    record.setStatus(status);
    if (status == 1) {
        record.setNextRetryTime(null); // 已确认的消息不再参与补偿
    }
    localMessageMapper.updateById(record);
}
```

1. **不带 cd 发送 = 回调永远不触发**——三参重载 `convertAndSend(exchange, key, msg)` 没有回执通道；
2. **回调触发 ≠ 发送成功**——要看 `result.isAck()`，nack 也走这个回调；
3. **cd.getId() 必须等于本地消息表的 message_id**——回执到达时全靠它反查记录。



### 4. 补偿：retrySend + 定时扫描

```java
/** 扫描条件：状态还没闭环 + 到了允许重试的时间 */
public List<LocalMessage> findTimeoutUnconfirmed() {
    return localMessageMapper.selectList(
        Wrappers.<LocalMessage>lambdaQuery()
            .in(LocalMessage::getStatus, 0, 2)              // SENDING 或 FAIL
            .lt(LocalMessage::getNextRetryTime, LocalDateTime.now()));
}

/** 补偿重发一条：指数退避，最多 3 次，耗尽转 DEAD 人工 */
   public boolean retrySend(LocalMessage msg) {
        if (msg.getRetryCount() >= 3) {
            msg.setStatus(3); // DEAD
            msg.setNextRetryTime(null);
            localMessageMapper.updateById(msg);
            log.error("[补偿] 消息 {} 重试耗尽，转为死信状态，需人工处理", msg.getMessageId());
            return false;
        }
        try {
            Object payload = JSONUtil.parse(msg.getContent());
            send(msg.getMessageId(), msg.getExchange(), msg.getRoutingKey(), payload);
            msg.setRetryCount(msg.getRetryCount() + 1);
            // 指数退避：下次重试时间 = now + 30s * 2^retryCount（30s -> 60s -> 120s）
            long backoff = 30_000L * (1L << msg.getRetryCount());
            msg.setNextRetryTime(LocalDateTime.now().plusNanos(backoff * 1_000_000));
            localMessageMapper.updateById(msg);
            log.info("[补偿] 消息 {} 第 {} 次重发完成", msg.getMessageId(), msg.getRetryCount());
            return true;
        } catch (Exception e) {
            log.error("[补偿] 消息 {} 重发失败", msg.getMessageId(), e);
            return false;
        }
    }
```

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class CompensationTask {
    private final LocalMessageSender sender;

    /** 每 30 秒扫一次（学习演示用高频；生产一般 1~5 分钟） */
     @Scheduled(fixedDelay = 30_000)
    public void compensate() {
        List<LocalMessage> pending = sender.findTimeoutUnconfirmed();
        if (pending.isEmpty()) {
            return;
        }
        log.info("[补偿任务] 发现 {} 条超时未确认消息，开始重发", pending.size());
        for (LocalMessage msg : pending) {
            sender.retrySend(msg);
        }
    }
}
```

要点拆解：

- **扫描条件为什么是 `status IN (0,2)`？** 0（SENDING）覆盖「ack 丢了/进程崩了/还没来得及发」，2（FAIL）覆盖「收到 nack/发送抛异常」。1（CONFIRMED）已闭环不碰，3（DEAD）等人工不碰。
- **为什么按 `next_retry_time` 过期才扫？** 指数退避的实现就落在这里：每次重发把`next_retry_time` 推远一倍，MQ 长时间宕机时重试频率自动衰减（30s→60s→120s），不雪上加霜。
- **为什么从库里还原 payload 而不是重发内存对象？** 补偿任务通常在另一个线程/另一次进程生命周期里跑，内存对象早没了；库里那份 JSON 才是唯一可信的「原文」。
- **重试上限 3 次 + DEAD 状态**：3 次都失败大概率是配置错误/严重故障，机器重试无意义，转人工排查（就像消费端的 error.queue 思路——机器兜到底，人兜最后一步）。

### MqCallbackConfig

```java
@Slf4j
@Configuration
public class MqCallbackConfig {

    /**
     * 全局 ReturnsCallback
     * 仅当【消息成功到达交换机，但路由不到任何队列】时触发
     * （前提：application.yaml 里 publisher-returns: true）
     */
    @Bean
    public SmartInitializingSingleton returnsCallbackInitializer(RabbitTemplate rabbitTemplate,
                                                                 LocalMessageSender localMessageSender) {
        return () -> {
            rabbitTemplate.setReturnsCallback(returned -> {
                log.error("【MQ消息路由失败】触发退回机制(Return)!");
                log.error("============== 失败详情 ==============");
                log.error("交换机(Exchange): {}", returned.getExchange());
                log.error("路由键(RoutingKey): {}", returned.getRoutingKey());
                log.error("应答码(ReplyCode): {}", returned.getReplyCode());
                log.error("应答文本(ReplyText): {}", returned.getReplyText());
                log.error("消息内容(Message): {}", new String(returned.getMessage().getBody()));
                log.error("=====================================");

                // ---- 实战补偿：把本地消息表状态改为 FAIL，交给补偿任务重发 ----
                // 从退回消息的头里取出发送时的 CorrelationData.id（= 本地消息表的 messageId）
                String messageId = returned.getMessage().getMessageProperties()
                        .getHeader("spring_returned_message_correlation");
                if (messageId != null) {
                    log.error("[Return补偿] messageId={} 路由失败，本地消息表状态改为 FAIL，等待补偿重发", messageId);
                    localMessageSender.updateStatus(messageId, 2);
                } else {
                    // 不带 CorrelationData 发送的消息（如纯测试消息）没有线索可改表，只能告警
                    log.error("[Return补偿] 该消息未携带 CorrelationData，无法定位本地消息表记录，请人工排查路由配置");
                }
            });
            log.info("[MqCallbackConfig] 全局 ReturnsCallback 已挂载（含本地消息表补偿）");
        };
    }
}
```

### ProducerController

```java
@Slf4j
@RestController
@RequiredArgsConstructor
public class ProducerController {

    private final RabbitTemplate rabbitTemplate;
    private final LocalMessageSender sender;
    private final LocalMessageMapper localMessageMapper;

    /**
     * 【本地消息表全流程】
     * curl -X POST "http://localhost:8104/order"
     * 预期（按顺序）：
     *   1. [本地消息表] 落库成功（事务内，状态 SENDING）
     *   2. 事务提交后 [MQ] 消息已发送 + [局部Confirm] ack -> 状态 CONFIRMED
     *   3. [下游stub] 收到订单支付消息
     */
    @PostMapping("/order")
    @Transactional(rollbackFor = Exception.class)
    public String order(@RequestParam(defaultValue = "ORD-1001") String orderNo) {
        String messageId = "PAY-" + UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        Map<String, Object> payload = new HashMap<>();
        payload.put("messageId", messageId);
        payload.put("orderNo", orderNo);
        payload.put("payAmount", 899900);

        // 第 1 步：事务内落库（本方法有 @Transactional，落库与「业务」同生共死）
        sender.saveMessage(messageId, "ORDER_PAID", payload,
                ProducerTopology.ORDER_EXCHANGE, ProducerTopology.ORDER_KEY);
        // 第 2 步：注册事务提交后自动发送（messageType 落库时已存，发送参数里不再重复）
        sender.sendAfterCommit(messageId, payload,
                ProducerTopology.ORDER_EXCHANGE, ProducerTopology.ORDER_KEY);
        return "下单完成 messageId=" + messageId + "，看控制台 落库->发送->ack 全流程";
    }
}
```

### LocalMessageSender

```java
@Slf4j
@Component
public class LocalMessageSender {

    private final RabbitTemplate rabbitTemplate;
    private final LocalMessageMapper localMessageMapper;

    public LocalMessageSender(RabbitTemplate rabbitTemplate,
                              LocalMessageMapper localMessageMapper) {
        this.rabbitTemplate = rabbitTemplate;
        this.localMessageMapper = localMessageMapper;
    }

    /**
     * 第一步：在业务事务内调用，把「要发的消息」先存进本地消息表（状态=SENDING）
     * 必须在 @Transactional 事务里调用，才会和业务数据一起提交/回滚。
     */
    public void saveMessage(String messageId, String messageType,
                            Object payload, String exchange, String routingKey) {
        try {
            LocalMessage msg = new LocalMessage();
            msg.setMessageId(messageId);
            msg.setMessageType(messageType);
            // 消息体统一转 JSON 存储（Hutool）—— 与真正发到 MQ 的内容保持一致
            msg.setContent(JSONUtil.toJsonStr(payload));
            msg.setExchange(exchange);
            msg.setRoutingKey(routingKey);
            msg.setStatus(0); // SENDING
            msg.setRetryCount(0);
            msg.setCreateTime(LocalDateTime.now());
            msg.setNextRetryTime(LocalDateTime.now().plusSeconds(30)); // 30s 未确认才允许补偿
            localMessageMapper.insert(msg);
            log.info("[本地消息表] 落库成功 messageId={} exchange={} routingKey={}",
                    messageId, exchange, routingKey);
        } catch (Exception e) {
            throw new RuntimeException("本地消息表落库失败", e);
        }
    }

    /**
     * 第二步：真正发送消息（应在事务提交后调用，见 sendAfterCommit）
     *
     * 【CorrelationData 的 id = messageId】是 Confirm 闭环的关键（笔记 §3.3.2 局部 ConfirmCallback）：
     * MQ 返回回执时，靠这个 id 反查本地消息表并更新状态。
     */
    public void send(String messageId, String exchange, String routingKey, Object payload) {
        // 1. 创建 CorrelationData，id 用消息唯一标识
        CorrelationData cd = new CorrelationData(messageId);

        // 2. 局部 ConfirmCallback（Boot 2.7 的 getFuture() 返回 ListenableFuture，用 addCallback）
        cd.getFuture().addCallback(result -> {
            if (result != null && result.isAck()) {
                log.info("[局部Confirm] 收到 ack, messageId={}", messageId);
                updateStatus(messageId, 1); // CONFIRMED
            } else {
                String reason = result == null ? "unknown" : result.getReason();
                log.error("[局部Confirm] 收到 nack, messageId={}, reason={}", messageId, reason);
                updateStatus(messageId, 2); // FAIL，等补偿任务重发
            }
        }, ex -> {
            log.error("[局部Confirm] Future 异常, messageId={}", messageId, ex);
            updateStatus(messageId, 2); // FAIL
        });

        // 3. 发送消息（携带 cd；JSON 转换器自动把对象转 JSON）
        rabbitTemplate.convertAndSend(exchange, routingKey, payload, cd);
        log.info("[MQ] 消息已发送 exchange={} routingKey={} messageId={}", exchange, routingKey, messageId);
    }

    /**
     * 便捷方法：注册「事务提交后再发送」的钩子。
     * 【为什么不在事务里直接发？】事务最终回滚的话，消费者会收到「业务根本没发生」的幽灵消息。
     */
    public void sendAfterCommit(String messageId,
                                Object payload, String exchange, String routingKey) {
        if (TransactionSynchronizationManager.isSynchronizationActive()) {
            TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    send(messageId, exchange, routingKey, payload);
                }
            });
        } else {
            send(messageId, exchange, routingKey, payload);
        }
    }

    /** 更新本地消息表状态（Confirm 回执按 messageId 反查记录后更新） */
    public void updateStatus(String messageId, int status) {
        LocalMessage record = localMessageMapper.selectOne(
                Wrappers.<LocalMessage>lambdaQuery().eq(LocalMessage::getMessageId, messageId));
        if (record == null) {
            log.warn("[本地消息表] 找不到 messageId={} 的记录", messageId);
            return;
        }
        record.setStatus(status);
        if (status == 1) {
            record.setNextRetryTime(null); // 已确认的消息不再参与补偿
        }
        localMessageMapper.updateById(record);
    }

    /** 查询超时未确认的消息（补偿任务用） */
    public java.util.List<LocalMessage> findTimeoutUnconfirmed() {
        return localMessageMapper.selectList(
                Wrappers.<LocalMessage>lambdaQuery()
                        .in(LocalMessage::getStatus, 0, 2)   // SENDING 或 FAIL
                        .lt(LocalMessage::getNextRetryTime, LocalDateTime.now()));
    }

    /** 补偿重发一条消息（指数退避，最多 3 次，耗尽转 DEAD） */
    public boolean retrySend(LocalMessage msg) {
        if (msg.getRetryCount() >= 3) {
            msg.setStatus(3); // DEAD
            msg.setNextRetryTime(null);
            localMessageMapper.updateById(msg);
            log.error("[补偿] 消息 {} 重试耗尽，转为死信状态，需人工处理", msg.getMessageId());
            return false;
        }
        try {
            Object payload = JSONUtil.parse(msg.getContent());
            send(msg.getMessageId(), msg.getExchange(), msg.getRoutingKey(), payload);
            msg.setRetryCount(msg.getRetryCount() + 1);
            // 指数退避：下次重试时间 = now + 30s * 2^retryCount（30s -> 60s -> 120s）
            long backoff = 30_000L * (1L << msg.getRetryCount());
            msg.setNextRetryTime(LocalDateTime.now().plusNanos(backoff * 1_000_000));
            localMessageMapper.updateById(msg);
            log.info("[补偿] 消息 {} 第 {} 次重发完成", msg.getMessageId(), msg.getRetryCount());
            return true;
        } catch (Exception e) {
            log.error("[补偿] 消息 {} 重发失败", msg.getMessageId(), e);
            return false;
        }
    }
}
```

### CompensationTask

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class CompensationTask {

    private final LocalMessageSender sender;

    /** 每 30 秒扫一次（学习演示用高频；生产一般 1~5 分钟） */
    @Scheduled(fixedDelay = 30_000)
    public void compensate() {
        List<LocalMessage> pending = sender.findTimeoutUnconfirmed();
        if (pending.isEmpty()) {
            return;
        }
        log.info("[补偿任务] 发现 {} 条超时未确认消息，开始重发", pending.size());
        for (LocalMessage msg : pending) {
            sender.retrySend(msg);
        }
    }
}
```

## 6. 异常场景

**场景一：消息还没发出去，进程崩了**

```
时间线：saveMessage 落库(status=0) → COMMIT → ✖ 进程崩溃（send 从未执行）
恢复：进程重启 → 30 秒后补偿任务扫描 → status=0 且 next_retry_time 已过期 → 重发 → ack → status=1
```

消息记录跟着业务事务一起落了盘，崩溃杀不掉它——**这就是「先落库」的意义**。



**场景二：ack 在网络中丢了**

```
时间线：send 发出 → MQ 收到入队 → ack 丢失 → 生产者这边 status 停在 0
恢复：补偿任务 30 秒后扫描 → 误判为「没送到」→ 重发 → MQ 会收到两遍
```

注意：**系统「不知道」这是误判，也不可能知道**——ack 丢了和没送到，在生产者视角完全一样。所以必然产生重复投递，这正是「消费端必须幂等」的根本原因。



**场景三：MQ 收到但返回 nack（交换机内部异常）**

```
时间线：send → nack 回执 → Future 回调立即触发 → status=2（不用等扫描）
恢复：补偿任务扫到 status=2 → 重发
```

局部 Confirm 回调的价值：把「感知失败」从「最慢 30 秒（定时扫描）」提前到「毫秒级」，
但**无论多快感知，挽回动作都只有一种——从库里拿原文重发**。



**场景四：路由键写错（Return 场景）**

```
时间线：send → 交换机收到但路由不到队列 → Return 退回（同时 ack=true）
```

这个场景 Confirm 会给 **ack**（消息确实到达交换机了），status 会变成 1——
**本地消息表管不到路由失败**！它由 Return 回调负责：全局 ReturnsCallback 打日志告警，
生产上还应在回调里把对应 messageId 标记为 FAIL，交给补偿链路。

> 三个回调各管一段：**Return 管路由、Confirm 管送达、本地消息表管最终一致**，谁也替代不了谁。



## 7. 状态机全景与人工兜底

```
                    ┌─────────────────────────────────────────┐
                    │  0 SENDING（落库后的初始状态）              │
                    └────┬────────────────────┬───────────────┘
                  ack ✓  │                    │ nack / 发送异常 / 30s 超时
                         ▼                    ▼
              ┌────────────────┐    ┌──────────────────────────┐
              │ 1 CONFIRMED ✅ │    │ 2 FAIL（等补偿扫描）        │
              │   (终点)       │    └────┬─────────────────────┘
              └────────────────┘         │ 补偿重发（retryCount+1，退避30s→60s→120s）
                                         │ 成功 → 1 / 依旧失败 → 保持2
                                         ▼ retryCount ≥ 3
                              ┌────────────────────┐
                              │ 3 DEAD（转人工）      │
                              │  修复后可手动重置状态  │
                              └────────────────────┘
```

DEAD 不是垃圾箱，是**人工处理队列**：故障修复后，把记录的 status 改回 2（或直接调重发接口），消息还能被再次投出。本地消息表让「人」成为可靠性的最后一环，而不是让消息凭空消失。



## 8. 补偿必然导致重复投递

回到场景二：你**永远无法**区分「MQ 没收到」和「MQ 收到了但 ack 丢了」。补偿任务只能盲目重发——这是「宁可重复、不可丢失」的主动选择。

由此得出全篇最重要的公式：

> **发送端「至少一次」（At Least Once） + 消费端「幂等」 = 业务上「恰好一次」（Effectively Once）**

这两层是**配套工程**，缺一不可：

| 组合 | 结果 |
|---|---|
| 只有本地消息表（至少一次） | 消息重复，积分加两次、短信发两条 |
| 只有消费端幂等（不做可靠发送） | 消息丢了就是丢了，幂等无从谈起 |
| 两者结合 | 丢不了 + 不会重复 = 业务正确 ✅ |

所以看到本地消息表的代码时，请同时检查消费端有没有幂等设计（Redis SETNX + 唯一索引）。
