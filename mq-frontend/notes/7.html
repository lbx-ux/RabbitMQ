死信交换机 · 延迟插件

1. 死信交换机

死信交换机（Dead Letter Exchange, DLX）用于接收处理失败或超时的异常消息。当消费者配合手动确认并拒签消息（requeue = false）时，Broker 会自动将该消息转发至绑定的 DLX 并写入死信队列（DLQ），避免消息丢失或陷入无休止的重试死循环。

触发死信的三种场景

  1. 拒签不重排：消费者调用 basicNack 或 basicReject，并将 requeue 设为 false。
  2. 消息 TTL 过期：消息在队列中存活时间超过了设置的 TTL（Time To Live）。
  3. 队列达到最大长度：队列积压达到上限（x-max-length），最早入队的消息被剔除。

DLX 核心配置

配置死信机制的关键是在声明正常队列时，通过队列参数指定 x-dead-letter-exchange 和 x-dead-letter-routing-key。

@Configuration
public class RabbitConfig {

    // 1. 声明死信 Exchange 与 死信 Queue
    @Bean
    public DirectExchange deadLetterExchange() {
        return new DirectExchange("dlx.exchange");
    }

    @Bean
    public Queue deadLetterQueue() {
        return new Queue("dlx.queue");
    }

    @Bean
    public Binding deadLetterBinding() {
        return BindingBuilder.bind(deadLetterQueue()).to(deadLetterExchange()).with("dlx.routing.key");
    }

    // 2. 声明正常 Queue 并关联死信参数
    @Bean
    public Queue normalQueue() {
        Map<String, Object> args = new HashMap<>();
        args.put("x-dead-letter-exchange", "dlx.exchange");         // 指定死信交换机
        args.put("x-dead-letter-routing-key", "dlx.routing.key");    // 指定死信路由键

        return new Queue("normal.queue", true, false, false, args);
    }
}

结合手动确认的具体工作流程

1.消息推送与接收：正常队列。

Broker 从 normal.queue 将消息推送给消费者，通道内部将该消息状态置为 Unacked。

2.业务逻辑处理失败：异常捕获。

消费者执行业务逻辑，由于数据校验失败、三方接口挂掉或代码异常，触发 try-catch 捕获。

3.拒签且禁止重入队：basicNack。

消费者在 catch 块中调用 channel.basicNack(deliveryTag, false, false)。将最后一个参数 requeue 设置为 false 是触发死信机制的关键步骤。

4.Broker 路由死信：DLX 触发。

Broker 收到拒签信号，识别到 requeue=false，查验当前队列配有 x-dead-letter-exchange，随后将消息打包投递给 dlx.exchange。

5.死信归档与二次处理：DLQ 存储。

死信交换机根据 dlx.routing.key 将消息写入 dlx.queue。专用的死信监听器或告警服务读取该队列，实现人工排查、日志落盘或延迟重试。

死信消息的关键特征（x-death 请求头）

消息进入死信队列后，RabbitMQ 会自动在消息 Header 中注入一个名为 x-death 的数组，里面包含了异常分析的关键元数据：

  • reason：死信原因（rejected 拒签、expired 过期、maxlen 队列超长）。
  • queue：消息死亡前所在的原始队列名称。
  • time / count：进入死信的时间戳以及该消息进入死信的次数。

2. 延迟消息

延迟消息：生产者发送消息时指定一个时间，消费者不会立刻收到消息，而是在指定消息之后才收到消息

延迟任务：设置在一定时间之后才执行的任务

在电商的支付业务中，对于一些库存有限的商品，为了更好的用户体验，通常都会在用户下单时立刻扣减商品库存。例如电影院购票、高铁购票，下单后就会锁定座位资源，其他人无法重复购买。

但是这样就存在一个问题，假如用户下单后一直不付款，就会一直占有库存资源，导致其他客户无法正常交易，最终导致商户利益受损！

因此，电商中通常的做法就是：对于超过一定时间未支付的订单，应该立刻取消订单并释放占用的库存。

例如，订单支付超时时间为30分钟，则我们应该在用户下单后的第30分钟检查订单支付状态，如果发现未支付，应该立刻取消订单，释放库存。

但问题来了：如何才能准确的实现在下单后第30分钟去检查支付状态呢？

像这种在一段时间以后才执行的任务，我们称之为延迟任务，而要实现延迟任务，最简单的方案就是利用MQ的延迟消息了。

在RabbitMQ中实现延迟消息也有两种方案：

  • 死信交换机+TTL
  • 延迟消息插件

1. DLX + TTL

死信交换机实现延迟消息的核心机制是 “TTL（生存时间） + DLX（死信交换机）” 的组合拳：把消息发送到一个没有消费者监听的暂存队列中，并设置过期时间；当消息超时过期后会自动变成“死信”，被 Broker 转发到真正的业务队列供消费者消费。

1.投递至暂存队列：消息入队并开始计时。

生产者将消息发送到暂存队列（Buffer Queue）。该队列专门用来积压和倒计时，不能配置任何消费者。

2.暂存队列 TTL 到期：触发死信转移。

消息在暂存队列中停留，直到达到预设的 TTL（Time-To-Live）。

3.Broker 自动路由至 DLX：重定向到业务交换机。

TTL 到期后消息变为死信，Broker 根据暂存队列绑定的 x-dead-letter-exchange 和 x-dead-letter-routing-key 将其转发给死信交换机。

4.目标队列接收并消费：延迟时间结束，执行业务。

死信交换机将消息路由到最终的业务队列，监听该队列的消费者接收到消息并执行业务（如取消超时未支付订单）。

Spring Boot 配置代码示例

@Configuration
public class DelayRabbitConfig {

    // 1. 声明最终消费的业务交换机与队列
    @Bean
    public DirectExchange businessExchange() {
        return new DirectExchange("business.exchange");
    }

    @Bean
    public Queue businessQueue() {
        return new Queue("business.queue");
    }

    @Bean
    public Binding businessBinding() {
        return BindingBuilder.bind(businessQueue()).to(businessExchange()).with("business.key");
    }

    // 2. 声明暂存队列：绑定死信参数与队列级 TTL（如 30 分钟）
    @Bean
    public Queue delayBufferQueue() {
        Map<String, Object> args = new HashMap<>();
        args.put("x-dead-letter-exchange", "business.exchange");      // 过期后发往业务交换机
        args.put("x-dead-letter-routing-key", "business.key");       // 业务路由 Key
        args.put("x-message-ttl", 30 * 60 * 1000);                   // 统一延迟 30 分钟

        return new Queue("delay.buffer.queue", true, false, false, args);
    }
}

致命踩坑点：队头阻塞问题（Head-of-Line Blocking）

如果在发送单条消息时动态设置消息的 TTL（如 messageProperties.setExpiration("10000")），会导致队头阻塞：

  • 原理：RabbitMQ 只会检查队列头部的消息是否过期。
  • 现象：如果先入队了一条 TTL 为 30 分钟的消息，紧接着入队了一条 TTL 为 10 秒的消息，后入队的消息无法按时过期，必须等队头 30 分钟的消息过期被移走后才会被处理。

最佳实践建议

  • 定长延迟阶梯：如果延迟时间相对固定（如 5 秒、10 分钟、30 分钟），针对每个时间段分别建一个暂存队列，不要给单条消息设动态 TTL。
  • 任意动态延迟：如果需要精确到任意秒级的动态延迟，建议直接使用官方的 rabbitmq-delayed-message-exchange 插件，该插件在 Exchange 层维护基于时间轮（Time Wheel）的延迟逻辑，从根本上解决队头阻塞。

2. DelayExchange插件

正常情况下，RabbitMQ 的交换机（Exchange）是不存储消息的，它只负责路由。 但安装了该插件后，会新增一种交换机类型：x-delayed-message。

  1. 暂存消息： 当生产者发送带有延迟时间标记的消息到该交换机时，交换机不会立即路由，而是将消息暂存在 RabbitMQ 的内部数据库（Mnesia）中。
  2. 到期路由： 交换机会在内部启动定时器，当消息的延迟时间到达后，交换机才会根据 Routing Key 将消息投递到绑定的目标队列中。
  3. 消费： 消费者在目标队列中监听并正常消费消息。

1. 部署

第一阶段：准备插件文件

  1. 根据你的 RabbitMQ 版本（如 3.12），去官方 GitHub 发布页下载对应的 .ez 格式插件包（例如：rabbitmq_delayed_message_exchange-3.12.0.ez）。插件下载地址：GitHub - rabbitmq/rabbitmq-delayed-message-exchange: Delayed Messaging for RabbitMQ
  2. 先将文件下载到你的物理机（Windows）电脑上。

第二阶段：Windows -> Linux 虚拟机

  1. 打开你常用的 SSH 客户端工具（如 FinalShell、Xftp、MobaXterm 等），连接到你的 Linux 虚拟机。
  2. 将 Windows 上的 .ez 文件拖拽或上传到虚拟机内部的某个目录下（例如上传到 /root 目录）。

第三阶段：Linux 虚拟机 -> Docker 容器

  1. 在虚拟机的 SSH 终端里，使用 cd 命令切换到你刚才存放文件的目录。

  2. 执行 docker cp 命令，将宿主机上的文件强行拷贝到 RabbitMQ 容器的官方插件目录中：

bash docker cp rabbitmq_delayed_message_exchange-3.12.0.ez rabbitmq:/plugins

(注：命令中的 rabbitmq 是你的容器名称，/plugins 是容器内的目标路径)

第四阶段：激活与重启

  1. 在虚拟机终端里，通过 docker exec 进入容器内部执行开启插件的命令：

bash docker exec -it rabbitmq rabbitmq-plugins enable rabbitmq_delayed_message_exchange

  1. 重启该容器，让配置彻底加载并生效：

bash docker restart rabbitmq

(注：只要执行过一次 enable，配置就会自启动，后续重启虚拟机或容器都不需要再重新配置)

第五阶段：最终验证

  1. 在 Windows 浏览器中打开 RabbitMQ 管理后台（http://192.168.146.130:15672）。
  2. 点击 Exchanges 标签页，展开底部的 Add a new exchange 面板。
  3. 点击 Type 旁边的下拉菜单，如果列表里出现了 x-delayed-message 选项，即代表部署圆满成功。

2. 声明延迟交换机

基于注解方式：

@RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = "delay.queue", durable = "true"),
        exchange = @Exchange(name = "delay.direct", delayed = "true"),
        key = "delay"
))
public void listenDelayMessage(String msg){
    log.info("接收到delay.queue的延迟消息：{}", msg);
}

基于@Bean的方式：

@Slf4j
@Configuration
public class DelayExchangeConfig {

    @Bean
    public DirectExchange delayExchange(){
        return ExchangeBuilder
                .directExchange("delay.direct") // 指定交换机类型和名称
                .delayed() // 设置delay的属性为true
                .durable(true) // 持久化
                .build();
    }

    @Bean
    public Queue delayedQueue(){
        return new Queue("delay.queue");
    }

    @Bean
    public Binding delayQueueBinding(){
        return BindingBuilder.bind(delayedQueue()).to(delayExchange()).with("delay").noargs();
    }
}

3. 发送延迟消息

发送消息时，必须通过x-delay属性设定延迟时间：

@Test
void testPublisherDelayMessage() {
    // 1.创建消息
    String message = "hello, delayed message";
    // 2.发送消息，利用消息后置处理器添加消息头
    rabbitTemplate.convertAndSend("delay.direct", "delay", message, msg -> {
    // 依然使用 Spring 提供的便捷方法
    msg.getMessageProperties().setHeader("x-delay", delayMillis);
    return msg;
});
}

3. 对比

死信队列（TTL + DLX）方案是基于原生队列存活过期的固定阶梯延时实现，而延迟插件（rabbitmq-delayed-message-exchange）则是基于 Exchange 内部存储机制的任意动态延时实现。

比较维度 死信队列方案（TTL + DLX） 延迟交换机插件方案
实现原理 消息在暂存 Queue 存活到期后，作为死信由 DLX 转发至业务 Queue 消息暂存在 Exchange 内部存储（Mnesia），到期后再路由给 Queue
任意动态延时 ❌ 仅建议固定阶梯延时（消息级 TTL 会引发队头阻塞） ✅ 支持单条消息指定任意秒级/毫秒级精确延时
队头阻塞风险 ⚠️ 单队列多 TTL 时存在严重队头阻塞 ✅ 彻底解决队头阻塞
环境依赖 ✅ 原生支持，无需安装任何插件 ⚠️ 需要所有 Broker 节点单独安装插件
拓扑复杂度 ⚠️ 较高（需要维护暂存 Queue、死信 Exchange 与目标 Queue） ✅ 极低（仅需 1 个延迟 Exchange + 1 个目标 Queue）
性能与高可用 ✅ 基于标准队列存储与复制，高并发吞吐能力强，高可用成熟 ⚠️ 消息积压在 Exchange 层，超大规模（百万级）时内存/磁盘压力大

死信队列方案（TTL + DLX）

  • 优势：开箱即用，无需改造 Broker 环境；依赖 RabbitMQ 原生成熟的队列持久化与镜像/ Quorum 机制，性能稳定，抗突发大流量能力强。
  • 劣势：无法优雅支持任意动态时间；若需要多种延迟时间（如 5s、10m、30m），必须配置多个对应的暂存队列。
  • 适用场景：延时时间固定且规范的业务场景，例如电商订单统一 30 分钟未支付自动取消、支付结果阶梯式回调通知（如 10s、30s、1m、5m）。

延迟交换机插件方案

  • 优势：架构极简，无需针对不同延时建多个队列；单条消息直接通过 Header 指定 x-delay 毫秒值即可完成精准动态延时。
  • 劣势：强依赖第三方插件；延时消息存储在 Exchange 的 Mnesia 数据库中而非标准 Queue 中，当延迟消息量巨大或节点宕机恢复时，对资源开销与恢复时间有一定影响。
  • 适用场景：延时时间高度个性化、动态不固定的场景，例如用户自定义定时提醒（如“预定明天 14:20 提醒”）、会议预约通知、中小型规模的个性化任务调度。

选型标准：延迟时间固定或消息吞吐量极大时，优先选择 DLX + TTL 方案；延迟时间完全不固定且追求代码与架构简捷时，优先选择 延迟插件方案。
